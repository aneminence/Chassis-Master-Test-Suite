## 0. 使用须知与事实边界

本文件是 CMTS 的**产品目标与架构约束**，不等于对当前仓库、PCB、固件或量产状态的事实核验。任何 AI Agent 开始编码前，必须读取现有仓库 README、解决方案文件、依赖关系、接口定义、测试结果及实际 PCB 资料，建立“已实现 / 部分实现 / 计划中 / 未确认”的现状清单。不得仅根据本文推断功能已经存在。现有技术栈、操作系统、芯片、GNSS 精度、采样率、LEMO 引脚、PoE 功率及具体硬件能力均须实测或核验。

本文对**产品定位、品牌名称和四大产品线**作出基线决定；对**具体实现技术、协议细节和型号参数**提出建议，尚需设计评审。任何与当前代码、硬件约束冲突的目标，应提出兼容迁移方案，不得直接破坏现有功能。

## 1. 品牌定位与愿景

- 母品牌：**CMTS**
- 英文全称：**Chassis Master Test Suite**
- 中文全称：**底盘大师测试套件**
- 产品定位：**开放式汽车动态测试、数据采集、处理、分析与验证平台**。
- 核心理念：One Platform. Complete Testing.（统一平台，完整测试生态）
- 核心策略：软件与硬件解耦、开放兼容第三方设备、数据模型统一、测试算法可复用、硬件模块化、现场与离线一致。

CMTS 不是单一 Windows 软件，也不是一台独立 Logger；它由软件、硬件、传感器及测试解决方案组成。允许用户仅使用软件导入第三方文件，也允许自研主机独立记录，最终在统一平台中完成分析。

## 2. 四大产品线（品牌基线）

CMTS 的 C / M / T / S 四个字母分别对应四大系列。系列名属于产品分类，不强制插入每个独立产品的正式名称。

| 代号 | 英文系列 | 中文定位 | 主要产品/组合 |
|---|---|---|---|
| C | **Computing** | 软件计算平台 | CMTS Studio、CMTS Field |
| M | **Modules** | 硬件采集设备 | CMTS Logger、CMTS DAQ；未来可扩展 Gateway、Video |
| T | **Transducers** | 传感器及测量附件 | CMTS Wheel、Motion、Force、Travel、Pressure、Temperature |
| S | **Solutions** | 专业测试解决方案 | CMTS Dynamics、Safety、Energy；后续扩展 Ride 等 |

### 2.1 Computing（软件）

**CMTS Studio**：Windows 专业测试与分析客户端，作为功能最完整的桌面工作站。功能模块可包括：

- Data Manager：数据导入/导出、项目、会话与文件管理。
- TrackMap：地图、轨迹、坐标、空间分析。
- Data Analysis：曲线、统计、计算、滤波及多通道对比。
- Device Manager：自研与第三方设备的发现、配置、连接、诊断。
- Test Center：加速、制动、操稳、麋鹿、鱼钩等测试定义与执行。
- Video Analysis：视频与测量数据同步分析（规划功能，按需求实现）。
- Report Center：测试报告模板、生成与导出。

**重要：Report Center 是 Studio 内部功能，不是独立产品或产品线。TrackMap 同样是 Studio 内部模块。**

**CMTS Field**：Android 手机/平板现场客户端，面向驾驶员和试验工程师。优先支持设备连接、状态显示、开始/停止记录、实时仪表、测试任务选择、简单结果查看。手机与平板原则上共用业务逻辑，采用响应式布局；不要求初版复制 Studio 的全部高级分析功能。

### 2.2 Modules（硬件）

**CMTS Logger**：独立工作的综合数据记录主机，目标能力包括 GNSS/INS、CAN、传感器接入、实时数据服务、本地存储、设备状态与控制。其独立记录能力不应依赖 Windows/Android 持续在线。

**CMTS DAQ**：扩展数据采集设备，负责模拟量、数字量、脉冲/频率等通道的采样、信号调理、保护和同步，按硬件能力选择是否支持 CAN、以太网等。

**未来预留（未立项）**：CMTS Gateway（车载总线/协议网关）、CMTS Video（视频采集设备）。

**不设独立 CMTS Sync 产品线/设备作为当前目标**。时间同步是 Logger、DAQ、协议和软件的横向基础能力；如未来确有独立同步硬件的市场需求，再经产品评审新增。

### 2.3 Transducers（传感器）

- CMTS Wheel：轮速测量；有线版本优先，无线版本待技术评估。
- CMTS Motion：IMU、加速度、角速度等运动状态传感器。
- CMTS Force：踏板力、转向力、拉压力等。
- CMTS Travel：悬架行程、拉线位移等。
- CMTS Pressure：液压、气压等。
- CMTS Temperature：温度测量。

传感器不必全部自研。允许采购、集成和标定第三方传感器，但需清楚标识兼容性、量程、精度、校准及来源。LEMO 线束、天线、支架、转接件等作为 **CMTS Accessories** 配套分类，不增设第五大产品线。GNSS 天线属于附件，不应默认等同于独立 GNSS 测量传感器。

### 2.4 Solutions（解决方案）

Solutions 是按客户场景配置的**软件功能 + 主机 + 传感器 + 附件 + 测试模板/报告模板**的交付组合，不应另行复制一套软件代码。

- CMTS Dynamics：车辆动力学测试，涵盖加速、制动、操纵稳定性、麋鹿、鱼钩等。
- CMTS Safety：主动安全、稳定性、紧急避障及相关测试。
- CMTS Energy：能耗、续航与工况数据分析。
- CMTS Ride：平顺性、振动与冲击（后续预留）。
- Handling 作为 Dynamics 的子套件或功能包，不优先设置为与 Dynamics 并列的一级系列。

组合示例：**CMTS Dynamics Kit** = CMTS Studio + CMTS Logger + GNSS 天线/安装附件 + 对应测试模板与报告模板；轮速、DAQ 等按需选配。具体清单须按客户工况及测量要求核定。

## 4. 总体技术架构

推荐：**模块化单体 Studio + 跨平台核心能力 + 插件适配层 + 独立运行 Logger/DAQ**。不在第一阶段引入不必要的分布式微服务。

```text
CMTS 产品生态
├── Computing
│   ├── CMTS Studio (Windows)
│   └── CMTS Field (Android)
│        │
│        ▼
├── 应用服务 / 统一业务 API
│   ├── Device Management
│   ├── Session / Channel Management
│   ├── Test Engine / Signal Processing
│   ├── Time & Coordinate Services
│   ├── Storage / Replay / Reporting
│   └── Plugin Management
│        │
│        ▼
├── 数据与设备适配层
│   ├── CMTS Native Device Adapter
│   ├── Third-party Device Adapters
│   └── VBO / KML / CSV / MF4 等文件适配器
│        │
│        ▼
├── Modules: Logger / DAQ / 后续硬件
│        │
│        ▼
├── Transducers: Wheel / Motion / Force / ...
│
└── Solutions: Dynamics / Safety / Energy / ...
    （以上能力的配置、授权、模板及交付组合）
```

注意：文件导入适配器与实时设备驱动属于不同类型的插件；第三方设备协议能力须逐设备验证。支持 VBO 文件**不代表**能够实时控制 VBOX 设备。

## 5. 软件模块边界与依赖原则

建议目标模块（名称可随现有仓库调整，不得无依据强制重命名）：

| 模块 | 职责 | 明确禁止的耦合 |
|---|---|---|
| Domain | Device、Channel、Session、Sample、TestResult 等领域模型 | 不依赖 UI 或具体硬件 |
| Core | 信号处理、坐标变换、时间映射、数值计算 | 不直接调用厂商 SDK |
| Acquisition | 实时流接入、缓存、分发、背压与异常处理 | 不实现 UI |
| Devices | 设备发现、连接、配置、健康状态 | 不内嵌测试算法 |
| Storage | 原生记录文件、索引、元数据、回放 | 不依赖图表控件 |
| TestEngine | 测试定义、触发、状态机、判定与结果 | 不从 UI 图表读取数据 |
| Formats | VBO、KML、CSV、MF4 等解析与导出 | 不负责实时设备控制 |
| Plugins | 插件生命周期、版本、隔离及加载 | 不固化厂商逻辑 |
| Contracts | 协议、DTO、版本、接口约束 | 不依赖 UI 具体实现 |
| Studio / Field | UI、交互、可视化和用户工作流 | 不重复实现底层计算规则 |

建议依赖方向：`UI -> Application Services -> Domain/Core`。设备、存储、文件格式通过接口接入。所有外部设备转换为统一通道模型后再进入测试与分析系统。

当前若采用 C#/.NET，优先评估可复用类库；Android 技术方案待现有架构审计后决定。禁止仅凭规划文件断言当前工程已经采用某种框架。

## 6. 统一数据模型（核心契约）

所有来源（CMTS Logger、VBOX 文件、车辆 CAN、第三方 GNSS、CSV、KML 等）经适配后统一为**通道定义 + 采样序列 + 数据质量/来源信息**。

### 6.1 关键对象

- `DeviceId`：物理或逻辑设备唯一标识。
- `SourceId`：数据来源实例标识。
- `ChannelDefinition`：语义类型、单位、数据类型、坐标系、名义采样率、校准及质量定义。
- `ChannelInstanceId`：具体来源的通道实例；两个 GNSS 的 speed 不能混为同一个通道。
- `SampleBatch`：批量采样值、时间戳、质量标志及通道引用。
- `Session`：测试会话，关联设备、车辆、人员、通道、记录文件和测试结果。
- `Event`：触发、异常、标记及测试事件。
- `TestDefinition` / `TestResult`：测试配置、算法版本、输入通道映射和结果。

### 6.2 基本规则

1. 通道统一语义，如 `vehicle.speed`，但保留 GNSS、CAN 等来源差异。
2. 数值应采用明确的标准单位（例如速度 m/s），显示单位可由 UI 转换。
3. 时间戳必须明确时间域、参考历元和精度；不能把设备本地计数直接当作 UTC。
4. 保留原始时间戳、转换后的统一时间戳及同步质量，不能在没有证据时伪造同步精度。
5. 明确坐标参考系、纬经度格式、高度基准、姿态坐标系和轴向约定。
6. 原始数据优先保留，派生数据记录算法版本、参数与输入通道。
7. 采样率不同的通道不得默认逐点对齐，插值/重采样须显式选择。
8. 采样质量至少支持有效、缺失、超范围、不同步、估计/插值等状态。
9. GNSS 地速与 CAN 车速不能不加区分地混合，测试规则应指定信号来源和替代策略。

## 7. CMTS Logger 与 DAQ 职责边界

### 7.1 Logger

目标：自主采集、实时处理、记录、通信和诊断。PC/平板断开后继续记录；恢复连接后支持查询、下载与回放。优先实现：

- GNSS/INS 数据接入与状态；实际融合解算位置按现有硬件和软件能力决定。
- CAN / CAN FD 接口（若 PCB 与收发器支持）。
- 传感器接入（按具体电气通道能力实现）。
- 本地时间基准、时间戳及 PPS 同步机制。
- 本地可靠记录、掉电恢复与数据完整性校验。
- 实时数据服务、设备配置、日志、固件升级与设备健康状态。

### 7.2 DAQ

目标：扩展模拟量、数字量、脉冲/频率等输入能力；信号调理、供电、隔离保护和同步采样。DAQ 可与 Logger 组成系统，也可在技术允许时通过开放接口单独连接 Studio。DAQ 的同步精度、通道数和采样率需根据器件与实测决定。

### 7.3 当前物理接口规划（待 PCB 核验）

- 双 GNSS 天线接口。
- 6 个 6 芯 LEMO 连接器的目标外观/布局，其中 4 个倾向于传感器输入、2 个预留/扩展；**具体电气定义未确认**。
- CAN / CAN FD（具体通道数与接口形式待定）。
- Ethernet，PoE 供电能力待功耗预算与 PD 方案核验。
- 4G/5G 单天线外部接口的外观规划；模组、天线需求和通信能力待定。
- LOG 按钮及 GNSS、双天线、IMU、网络等状态指示灯。
- 外壳黑金色风格，金色内部框架与黑色外板方案需结合结构、散热和加工可行性验证。

**禁止假设：6 芯 LEMO 等于通用模拟量输入、PoE 一定足够供电、单天线一定满足蜂窝模组要求、外壳一定无需主动散热。** 先核查电路板、电源、散热、EMC、接口和防护设计。

## 8. 设备通信协议：CDP（拟议）

建议统一定义 `CMTS Device Protocol (CDP)`，将自研设备能力与上层软件解耦。具体协议形式需要硬件资源评审。

### 8.1 三个逻辑平面

| 平面 | 职责 | 候选实现 |
|---|---|---|
| Control | 发现、能力查询、配置、记录控制、诊断 | TCP + Protobuf/gRPC 或轻量二进制协议 |
| Telemetry | 实时采样流、状态、事件 | UDP/TCP；根据可靠性和时延要求选型 |
| File Transfer | 文件列表、下载、校验、续传 | HTTPS 或可靠 TCP 文件服务 |

### 8.2 最小 API

`DiscoverDevices`、`GetDeviceInfo`、`GetCapabilities`、`ConfigureChannels`、`StartRecording`、`StopRecording`、`SubscribeTelemetry`、`GetDeviceHealth`、`ListRecordings`、`DownloadRecording`。

### 8.3 必须定义的协议机制

- 版本协商与兼容矩阵；设备身份、序列号与权限控制。
- 明确的设备状态机：Idle / Configured / Recording / Finalizing / Error。
- 控制命令请求 ID、超时、重试、幂等与错误码。
- 数据包序号、时间戳、时间域、通道标识、质量标志。
- 断线续录、重连恢复、文件校验与固件升级回滚。
- 实时传输丢包不能影响 Logger 本地原始记录。
- 不把未加认证的设备控制接口直接暴露到公网。

## 9. 第三方兼容与插件规则

- 原生设备：CDP Adapter。
- VBOX：优先支持合法可解析的 VBO 等文件；实时连接需按型号、协议和授权核验。
- 通用 GNSS：NMEA / 厂商公开协议，按能力适配。
- CAN：通过兼容的厂商接口/驱动获取帧数据，再映射到通道。
- 文件格式：KML、GPX、CSV、VBO、MF4 等分别独立适配。
- 第三方驱动与不可信原生 SDK 宜采用独立进程隔离，防止导致 Studio 整体崩溃。
- 插件必须声明 API 版本、支持设备/格式、能力、依赖与异常处理规则。

## 10. 测试引擎与数据存储

### 10.1 Test Engine

统一测试定义：输入通道需求、算法版本、参数、触发条件、结束条件、有效性规则、输出指标与报告模板。相同算法尽量支持实时 Online 和离线 Offline 两种执行模式，并使用同一组标准数据集回归验证。安全相关测试结果须有质量标志和人工复核流程，不将未经验证的算法结果表述为认证结论。

### 10.2 数据存储

- 建议采用测量数据文件 + SQLite 元数据库的组合。
- SQLite 保存项目、会话、设备、通道索引、校准和报告元信息。
- 高频测量数据采用适合顺序写入、分块索引、校验与异常恢复的文件存储。
- 评估 ASAM MDF/MF4 作为原生或标准导出格式的可行性；避免无必要重复造格式。
- 导入、导出、回放须保留单位、坐标、时间基准、来源和数据质量。

## 11. 产品与技术发展阶段

| 阶段 | 产品目标 | 关键交付与验收 |
|---|---|---|
| P0：现状审计 | 保护已有 Studio 成果 | 仓库依赖图、功能盘点、构建与回归测试基线 |
| P1：平台核心 | Studio + 统一数据层 | Channel/Session 契约、解析适配、测试引擎分层 |
| P2：首台 Logger | 自研主机工程样机 | PCB 核验、接口定义、供电散热、独立记录、CDP 最小链路 |
| P3：软硬件闭环 | Studio ↔ Logger | 发现、配置、实时流、记录、下载、离线分析及断线恢复 |
| P4：扩展生态 | Field + DAQ + 传感器 | Android 客户端、扩展数采、传感器适配与时间同步验证 |
| P5：产品化 | Solutions 与交付体系 | 校准、诊断、兼容矩阵、文档、安装、版本管理与可靠性测试 |

建议先建立可验证的端到端闭环，再扩展产品数量。上述阶段不代表固定时间或已承诺的交付日期。

## 12. AI Agent 开发强制规则

1. **先读现状再改动**：每项任务先查仓库、README、构建文件、测试、接口资料及硬件约束。
2. **不得擅自重写**：保持现有 Windows 软件功能，采用可回退的渐进式重构。
3. **统一边界**：UI 不直接实现采样解析与测试算法；算法不直接读取图表控件；驱动不泄漏厂商特定类型到核心领域模型。
4. **接口先行**：修改跨模块数据结构或协议前，提交接口/契约设计和兼容影响说明。
5. **不虚构硬件能力**：未拿到原理图、PCB、BOM 或实测数据时，将引脚、性能和接口标记为待确认。
6. **保留开放性**：不得把 Studio 的核心分析功能绑定到必须拥有 CMTS Logger 才可运行。
7. **测试必备**：修改解析器、坐标、时间戳、算法和协议时增加单元、集成或黄金数据回归测试。
8. **数据可信**：所有结果标明来源、单位、时间域、质量和算法版本；不得静默丢弃异常数据。
9. **并行协作**：DSH、Grok Bot、Codex 各自使用分支/PR；明确文件所有权和接口契约，避免无协调地并行修改同一核心模块。
10. **交付透明**：每次 PR 报告改动范围、验证方法、测试结果、已知风险、回滚方式及未完成项。
11. **文档同步**：新增产品、接口、通道或数据格式时更新对应规范与兼容矩阵。
12. **区分状态**：明确标记 `Implemented`、`Partial`、`Planned`、`Unverified`，不得将规划描述写成已完成事实。
13. **注释重意图而非数量**：优先用命名、类型、小函数和测试形成自解释代码；只为业务原因、数据单位/时间域、协议与兼容约束、安全/并发/性能边界等代码无法可靠表达的信息添加注释。禁止逐行复述代码，也不以注释覆盖率为目标。修改代码时同步清理邻近的过期或误导注释，具体规则见 `AGENTS.md`。

## 13. AI Agent 标准任务流程

每个开发任务按以下步骤执行：

1. **Inspect**：读取当前仓库、相关代码、配置、硬件文档，输出当前实现与目标差距。
2. **Plan**：提出最小改动方案、涉及模块、API 变化、数据迁移与兼容风险。
3. **Approve**：对于架构变更、协议破坏性变更、硬件引脚/电源调整，先取得负责人确认。
4. **Implement**：在独立分支实施；不混入无关重构。
5. **Verify**：构建、单元测试、集成测试、真实数据回放；硬件相关需补充台架/实物验证。
6. **Review**：提交 PR、测试证据、问题清单及回滚方案。
7. **Document**：更新产品架构、协议、接口、版本和变更日志。

建议每次给 Agent 的任务模板：

```text
请将 CMTS_PRODUCT_ARCHITECTURE.md 作为产品与架构约束。
任务目标：<填写单一可验收目标>
先审计当前仓库/硬件资料，列出已实现、待实现及未知信息。
提出最小增量方案与验收测试，未经确认不要大规模重构。
保持开放兼容、统一数据模型与模块边界。
完成后提供变更文件、构建/测试结果、风险、回滚方案和文档更新。
```
