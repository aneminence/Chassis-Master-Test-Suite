# 角色与职责（CMTS 多 Agent）

本文件界定「谁决定需求」与「谁保证工程」——对应群 **CMTS开发** 与日常协作。

## 总原则

- **产品管理规范**：决定问题定义、范围、优先级、验收口径、Roadmap/PRD。
- **ECC / 工程工作流**（`AGENTS.md`、`.ai-workflows/custom/`）：决定实现质量、测试、审查、可否合入。
- **用户（维护者）**：最终拍板；含发版、是否做 Android MVP、是否合入某大分支等。
- 任一 Agent **不得**用对方领域的文件覆盖对方决策（例如不得用 PRD 取消单测要求；不得用「代码已写完」倒逼扩大已批准范围）。

## 角色表

| 角色 | 典型身份 | 产品侧 | 工程侧 |
|------|----------|--------|--------|
| **用户 / 维护者** | 仓库 Owner | 批准 PRD、Roadmap、发版 | 授权合入 `main`、授权 bump |
| **Chief / Grok Bot** | 统筹 | 组织评估、催 PRD、对齐群结论；**不**私自改产品范围 | 协调开 PR、同步本机；不代替质量签字 |
| **CMTS 功能** | 功能实现 | 可提方案与工作量；落实已批准需求 | 主写功能代码、技术设计 |
| **CMTS 质量** | 测试与 CI | 可要求验收可测、标回归风险 | 单测、CI、重构卫生、合入后回归 |
| **CMTS 美化** | UI / VI | 可提信息架构与视觉约束进 PRD | 主题、布局、皮肤 tokens，不改分析语义 |
| **CMTS 试验** | 使用端 / 试车习惯 | 提出场边问题、走查路径、验收观感 | **不写主线代码**；不做黄金 VBO/Pass 草案（现行口径） |
| **产品文档作者** | 任一被指派写 PRD 者 | 维护 `docs/product/` 文稿 | — |

「ECC」在本仓库指：**工程与质量控制实践**（含功能 + 质量队友、verification-loop、code-review、测试项目），**不是**必须安装的全局插件。

## 决策矩阵（简）

| 问题 | 谁主决 | 谁咨询 |
|------|--------|--------|
| 做不做、做到哪一版 | 用户 ← 产品评估 | 功能（工作量）、试验（现场价值） |
| 优先级排序 | 用户 / Chief 按 `prioritization.md` | 全体 |
| 验收标准是否「像试车」 | 试验 + 用户 | 功能 |
| API/模块怎么拆、测什么 | 功能 + 质量 | 产品（仅当影响外部行为时回写 PRD） |
| 能否合入 `main` | 用户授权 + 工程检查通过 | — |
| 版本号 / 打包 | 仅用户按 `VERSIONING.md` 要求时 | — |

## 多 Agent 协作要点

1. **先文档后大码**：重大功能无「已批准」PRD（或等价书面范围）不铺开实现。
2. **群内同步**：范围变更在群里短讯同步，并改 PRD「变更记录」。
3. **试验后置**：功能合入或可跑包后，试验从使用端提问题；功能/质量/美化认领，不让试验改主线。
4. **美化与产品**：视觉可先行布局稿，但不得单独改变试验语义或通道含义。
5. **Android / 新客户端**：属 Computing 产品线新切片；未拍板前只停在 Roadmap 候选，不默认开干。

## English (short)

Product norms own *what/why/priority/acceptance*. ECC-style engineering owns *how/quality/merge readiness*. User is final approver. Field (试验) reports UX issues; does not own mainline code or version numbers.
